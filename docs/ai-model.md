# Predictive scaling decision

The current model is implemented in Python under [`model/`](../model/README.md). It is trained directly on the supplied real Azure Functions 2019 HTTP invocation traces. It forecasts the next two minutes of request demand and estimates surge probability. The research source, author implementation, exact training procedure, and held-out measurements are in the model guide.

The current v2 surge classifier uses richer past-only traffic features and was retrained on 3.26 million windows from 40% of Azure function hashes. A separate function group set calibration and threshold. Across five inspected evaluation groups, pooled surge precision was 45.81% and recall was 64.23%, both slightly higher than the earlier v2 artifact; one group regressed. This is exploratory evidence because the same groups have been used during model development. Neither measure reached 95%. The forecaster is the original compact v1 model. The active artifact is about 193 KB; Raspberry Pi performance remains unmeasured.

The Go controller owns monitoring, the API, and configured device control. Its `/api/prediction` endpoint exposes a cached Python result refreshed every 15 seconds. The Next.js dashboard shows traffic surge probability, forecast request rate, and model availability. With measured `MODEL_CAPACITY_RPM`, Python reports `would_wake` when predicted demand reaches capacity or when high surge risk and the upper estimate reach capacity; it otherwise reports `stay_primary`. By default `operational_scale_ready:false` keeps the result in shadow mode. Python never sends Wake-on-LAN or changes HAProxy. The [setup guide](windows-pi-setup.md#8-ai-behavior) documents the explicit operational validation switch and independent Go controller gate.

## Scaling policy once hardware is available

The implemented [deployment policy](windows-wireless-deployment.md) combines **validated AI for early activation with a sustained CPU trigger**. Warn at 60% primary CPU and request activation at or above 70% continuously for 15 seconds using distinct fresh Windows samples. A model risk score must be interpreted with measured single-server request capacity and the actual standby wake-to-healthy interval. The model predicts traffic demand, not CPU percentage, so it cannot enforce a 70% CPU ceiling. Missing model inputs or stale traffic make predictive activation unavailable while the CPU path remains usable with fresh inputs. The app-health failure path remains separate failover behavior. Wake once, wait for `/health` and proxy readiness, then serve from standby. This software path is tested with injected devices; physical capacity and wake validation remain pending.

This work is still pending because the Azure trace contains request counts but no CPU, latency, server capacity, startup time, or measured benefit of a second server for this project. The current surge classifier has substantial false alerts on held-out Azure days. Before activation, benchmark both laptops under the same workload, measure lead time and false wakes, and verify that routing to two machines improves latency and errors. The selected board is a Raspberry Pi 4 Model B; measure Python service memory and scoring time on it before relying on the model for a live demo.
